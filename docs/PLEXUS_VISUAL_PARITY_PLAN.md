# Trefoil parity rollout (approval draft)

## Decisions and boundary

- User selected **independent Trefoil**: keep its own PostgreSQL, providers, credentials, and traffic; Plexus at `http://100.121.114.16:4000/ui` is a read-only reference, never a data source or migration target.
- User selected **visual-first**: match Plexus's layout, navigation, information hierarchy, component sizing, interactions, and responsive states before completing every backend feature. **Do not copy Plexus colors or branding**; keep Trefoil name/mark and its own palette. Use **ECharts** for charts, not the reference chart implementation.
- Visual parity is not functional parity. Disabled or unavailable behavior must be labeled honestly, not rendered as a working button. Later slices will close backend/API differences independently.
- No unit tests are to be added. Verify user-visible flows with end-to-end tests and browser inspection.

## Decomposition: inputs, flow, and expected observations

1. **Reference and baseline.** Inputs: authenticated, read-only browser sessions at Trefoil `http://127.0.0.1:8080/` and Plexus `http://100.121.114.16:4000/ui`, matched desktop/mobile viewports, reference checkout `.reference/plexus` revision `7e959ff8`, and existing screenshots `/tmp/trefoil-dashboard.png` and `/tmp/plexus-dashboard.png`. Expected: route-by-route, state-by-state inventory with screenshots and accessibility snapshots. Browser state may expire; reauthenticate securely without printing secrets. The live Plexus deployment revision is not established by the local checkout hash. Never assume the two data sets should show the same metrics.
2. **Trefoil contracts.** Inputs: frontend `App.tsx`, `AppShell.tsx`, `Dashboard.tsx`, `ThemeContext.tsx`, `lib/api.ts`; backend router in `backend/src/lib.rs` and its merged modules. Flow: route → auth principal → page → adapter request → Rust handler/database → render loading/error/empty/data. Expected: preserve authenticated admin/limited boundaries, local storage behavior, API response shapes, and working controls while changing layout. Existing `frontend/e2e/control-plane.spec.ts` is the end-to-end test home.
3. **Visual layer first.** Inputs: Plexus `MainLayout.tsx`, `Sidebar.tsx`, dashboard tab hierarchy, and screenshots. Transform shared shell and dashboard structure using Trefoil palette and ECharts. Expected: comparable sidebar collapse/drawer, header/title/tab hierarchy, polling/window selectors, card order and responsive behavior, with honest empty data. No Plexus logos, copied production quota values, or dark palette. The existing app has `echarts-for-react` and uses it in the dashboard; avoid an unnecessary new chart library.
4. **Functional layers later.** For each route, map API inputs/responses, mutations, error states, security boundary, and persistence to Plexus reference. Implement independently against Trefoil storage and verify with user-visible E2E flows; do not count matching DOM or passing build as backend parity. Existing `PARITY_AUDIT.md` and `FULL_PARITY_ROADMAP.md` are leads, not current proof: some historical gap lists contradict later updates.

## Breaking points and ripple map

- `frontend/src/App.tsx` wraps routes in `ProtectedRoute`; shared shell changes affect every authenticated page, and the reference's limited-user redirects are stricter. Verify direct URLs and limited-user navigation rather than only the admin dashboard.
- `AppShell.tsx` owns the navigation and mobile overlay; collapse width changes affect the sticky header and main content offsets. Inspect every page at desktop and narrow viewport.
- `Dashboard.tsx` loads config, usage, recent records, concurrency and cooldowns via `Promise.allSettled`, polls while visible, and displays empty data. A visual tab must not duplicate polling or show stale/production-looking values. ECharts need resize after sidebar transitions and must retain accessible labels/empty states.
- `ThemeContext.tsx` defaults to light and persists `trefoil-theme`; preserve the chosen Trefoil palette instead of lifting reference tokens. Reference screenshot's dark theme is not a target requirement.
- The worktree already contains extensive user changes and untracked UI files. Review each file before editing, do not overwrite unrelated work or reinitialize the project, and avoid writing into `.reference/plexus`.
- Local reference checkout and live Plexus may differ; compare both the source revision and the browser-visible deployment, mark mismatches unknown until reconciled. Production data and quota widgets cannot be copied into local Trefoil.
